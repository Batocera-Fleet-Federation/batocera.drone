01 · The fleet, geographically

Three houses, one swarm

Every connector below is the same outbound mTLS peer channel — pairing, ROM/BIOS transfer, and VPN-credential sharing all ride over it. There is no separate network for any one of those jobs.

Same-network Drones (Portland) reach each other over the LAN with zero configuration. Cross-network pairs (Portland↔Berlin, Berlin↔Singapore) use a shared , which also carries the pairing handshake and, once a Drone opts in, its shared VPN credentials — nothing here uses a separate transport for "VPN sharing" versus "ROM sync." A legacy direct-WAN path exists for pairs without a tailnet, but needs a port-forward on both ends.

02 · Transport selection

Reaching a specific peer

Every transfer picks its own route independently — TransportSelector tries each tier best-first and falls through on failure.

This is app/transport/'s TransportSelector, used by every asset transfer and VPN config pulls alike. It's single-source P2P, not torrent-style swarming: one active transfer per job, from one chosen peer.

03 · Trust model

Pairing, once — then cert-pinned forever

No shared CA, no third party. A peer is trusted because, and only because, it's in this Drone's own paired-peer list.

Application authorization is exactly this list check — connectivity checks (every ~30s, cached locally) confirm a peer is reachable, never that it's authorized. The same mTLS identity backs ROM/BIOS/save/artwork transfers and the VPN peer endpoint alike.

04 · One machine, zoomed in

Inside a Drone

stdlib + . No database server, no message queue, no external runtime dependency.

The VPN manager is deliberately stateless — status() recomputes from /proc and the log on every poll rather than keeping cached state in sync with a thread. The process it spawns is fully daemonized (its own session, its own process group), so it survives a Drone-app restart untouched; only a full machine reboot takes it down, which is exactly what the startup bootstrap above exists to recover from.

05 · One subscription, the whole swarm

VPN: share once, only

Credentials travel only over the mTLS peer channel above — never through the browser-facing admin API, on either end.

Everyone in the swarm is presumed to be the same owner — pairing is the only authorization check, same as ROM/BIOS transfer. Two independent gates keep credential distribution single-hop: set_sharing_enabled() refuses to turn on for an imported config, and export_payload() refuses to serve one, even if the first check were ever bypassed.

SMTP email settings share this exact lifecycle over GET /peer/smtp/config (app/device/smtp_manager.py) — same off-by-default sharing_enabled gate, same single-hop provenance, same revocation poller. The one difference: SMTP's swarm-bootstrap has no "actively connected right now" check to wait for, since sending mail isn't a persistent tunnel — any paired peer that's sharing and returns a usable host qualifies immediately. See the drone-smtp-notifications skill for depth.
